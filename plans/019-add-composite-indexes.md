## Why this matters

Two hot read paths filter-then-aggregate / filter-then-sort on columns that have
no covering composite index:

1. `GET /api/v2/usage` runs `current_account.usage_events.where(status: "finalized")`
   and then sums/groups over the result. The `usage_events` table has indexes on
   `(account_id, created_at)`, `(account_id, model)`, and `(account_id)` — but
   **none covering `status`**. On accounts with many events, the filter falls
   back to an `account_id` index scan plus a filter on `status`.
2. `GET /api/v2/scribe_sessions` runs `where(account:).order(created_at: :desc)`.
   `scribe_sessions` has only `index_scribe_sessions_on_account_id` — **no
   `(account_id, created_at)`** — so the ordered list needs a separate sort.

Adding `usage_events (account_id, status)` and `scribe_sessions (account_id, created_at)`
lets Postgres satisfy each query from a single index. **But** at small
per-account volume the existing indexes may already be good enough, so this plan
requires you to confirm the planner actually uses the new indexes (via `EXPLAIN`
at representative volume) before committing them. The migration is reversible and
changes no application behavior.

## Steps

### Step 1: Write the migration

Create `db/migrate/20260708000001_add_composite_indexes_for_hot_filters.rb` with:

```ruby
class AddCompositeIndexesForHotFilters < ActiveRecord::Migration[8.0]
  def change
    # GET /api/v2/usage filters usage_events by (account_id, status='finalized').
    add_index :usage_events, [ :account_id, :status ],
              name: "index_usage_events_on_account_id_and_status",
              if_not_exists: true

    # GET /api/v2/scribe_sessions filters by account_id and orders by created_at DESC.
    add_index :scribe_sessions, [ :account_id, :created_at ],
              name: "index_scribe_sessions_on_account_id_and_created_at",
              if_not_exists: true
  end
end
```

`add_index` in `change` is reversible; `if_not_exists: true` makes re-runs safe.

## Maintenance notes

For whoever owns this after it lands:

- **Production deploy note:** `add_index` without `algorithm: :concurrently`
  takes an `ACCESS EXCLUSIVE`-ish lock that blocks writes while the index builds.
  On a large `usage_events`/`scribe_sessions` table in production, switch to a
  concurrent build: add `disable_ddl_transaction!` to the migration and
  `add_index ..., algorithm: :concurrently`. That form is **not** used here to
  keep the migration reversible and simple for CI/test; raise it if the target
  tables are already large in prod.
- **Partial-index alternative for usage:** if the workload is overwhelmingly
  `status = 'finalized'` reads, a partial index
  `add_index :usage_events, :account_id, where: "status = 'finalized'", name: "index_usage_events_on_account_id_where_finalized"`
  is smaller and can be faster than the full `(account_id, status)` composite.
  Step 3's EXPLAIN is the deciding evidence; the composite is chosen here as the
  simpler default.
- If `GET /api/v2/usage`'s `by_model` grouping becomes a hotspot, consider a
  wider `(account_id, status, model)` covering index — deferred; not justified
  without EXPLAIN evidence.
- Reviewer should scrutinize: the EXPLAIN plans in the PR description (both must
  show the new index chosen), that only the two intended indexes were added, and
  that `db/schema.rb`'s `version:` bumped to `2026_07_08_000001`.
